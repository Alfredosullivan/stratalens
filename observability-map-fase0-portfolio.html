01 · El problema

Tu arquitectura debería documentarse sola

Para entender una app full-stack, un desarrollador salta entre VS Code, GitHub, el CI/CD, la base de datos, los logs y las métricas, y arma el mapa mental a mano. No existe un lugar único que muestre visualmente cómo se conectan las piezas — ni en diseño (qué existe) ni en tiempo real (qué está pasando ahora). Este proyecto ataca eso.

La Fase 0 no dibuja el mapa todavía: construye los cimientos sobre los que se apoyará todo — una arquitectura limpia, un modelo de datos que se protege a sí mismo, persistencia real en PostgreSQL y autenticación segura con GitHub. Base sólida antes que features.

02 · Stack & decisiones

Cada tecnología, con su "¿por qué?"

¿Por qué .NET 10 + EF Core?

ASP.NET Core Web API

Backend tipado, maduro y con un ecosistema de seguridad de primera (Data Protection, autenticación integrada). EF Core para el acceso a datos detrás de abstracciones.

¿Por qué PostgreSQL y no Neo4j?

PostgreSQL (grafo sobre tablas)

Un grafo de nodos/edges no necesita una base de datos de grafos para consultas de 1-2 saltos. Postgres lo resuelve con índices, sin añadir una segunda tecnología de persistencia al MVP. Decisión reversible (aislada tras IGraphRepository).

¿Por qué React Flow (@xyflow/react)?

React 19 + Vite + React Flow

El canvas es el protagonista. React Flow da zoom, pan, nodos y edges custom. Se usó el paquete correcto y mantenido (@xyflow/react v12), no el antiguo reactflow.

¿Por qué Clean Architecture?

Domain / Application / Infrastructure / Api

El dominio no conoce frameworks; la infraestructura es un plug-in reemplazable. Cambiar la base de datos o el proveedor de código no toca la lógica de negocio.

¿Por qué cookie HttpOnly y no JWT?

GitHub OAuth + cookie de sesión

La cookie HttpOnly no es legible por JavaScript → protege contra XSS. GitHub solo se usa para el login externo; la sesión vive en la cookie. Más seguro que guardar un JWT en localStorage.

¿Por qué Testcontainers?

Data Protection · Testcontainers

El token de GitHub se cifra en reposo con la Data Protection API. Los tests de integración levantan un PostgreSQL real y efímero en Docker — sin mocks que mientan sobre el comportamiento de la DB.

03 · Arquitectura

La regla de dependencia, dibujada

Las dependencias apuntan siempre hacia adentro. El dominio, en el centro, no depende de nada.

        Api  ─────▶  Application  ─────▶  Domain
         │               ▲                  (sin dependencias)
         │               │
         └─▶ Infrastructure  (implementa IGraphRepository,
                              IUserRepository, ITokenProtector...)

  Frontend (React) ──REST/cookie──▶ Api      (nunca toca la DB ni GitHub directo)

Estructura del backend:

backend/
├── src/
│   ├── ObservabilityMap.Domain/        # Node, Edge, Project, User + invariantes
│   ├── ObservabilityMap.Application/    # Abstracciones (I...Repository) + casos de uso
│   ├── ObservabilityMap.Infrastructure/ # EF Core, GraphRepository, cifrado, migraciones
│   └── ObservabilityMap.Api/            # Controllers, OAuth, cookie, DI (composition root)
└── tests/
    ├── ObservabilityMap.Domain.Tests/        # 31 unit tests de invariantes
    ├── ObservabilityMap.Infrastructure.Tests/ # 4 integration (Testcontainers)
    └── ObservabilityMap.Api.Tests/            # 3 integration (auth + ownership)

04 · Lo construido

Features de la Fase 0

🧱 Modelo de dominio autoprotegido

Node, Edge, Project y User con estados ilegales irrepresentables: factory methods, propiedades inmutables y constructores privados. Un Edge nunca puede existir sin origen o con una confianza incoherente.

🔌 Sistema de plugins de analyzers

ILanguageAnalyzer permite añadir un stack nuevo sin tocar el pipeline (principio Open/Closed). Mismo patrón adapter para proveedores de código (IProviderConnector).

🗄️ Persistencia con EF Core + JSONB

Grafo en PostgreSQL con metadata en jsonb, guardado idempotente y transaccional (borra+inserta atómico), y lecturas AsNoTracking.

🔐 Login con GitHub (OAuth)

Flujo "Sign in with GitHub" con cookie HttpOnly, scopes mínimos (read:user, public_repo) y secretos fuera del repo (user-secrets).

🛡️ Token cifrado en reposo

El access_token se cifra con Data Protection API y se guarda como shadow property — la columna existe en la tabla pero no en el modelo de dominio. Verificado leyendo la columna cruda por SQL.

✅ Aislamiento entre usuarios

Ownership check en cada proyecto: acceder a un recurso ajeno devuelve 404 (no 403) para no filtrar su existencia. Probado con un test de acceso cruzado.

05 · Bugs reales resueltos

Diagnóstico de causa raíz, no parches

Conflicto de versiones de EF Core Build · CS1705

Síntoma: el proyecto de test no compilaba: "Infrastructure usa EF Core 10.0.12 pero se referencia 10.0.4".
Causa: el provider de Npgsql arrastraba EF Core 10.0.4, y EntityFrameworkCore.Design forzaba 10.0.12 en Infrastructure. Como Design es dependencia privada, el test solo veía la 10.0.4.
Fix: referencia directa (no privada) a Microsoft.EntityFrameworkCore.Relational 10.0.12 en Infrastructure para que la versión correcta fluya a los consumidores.

Connection string vacío en tests del Api Test · runtime

Síntoma: los tests de integración fallaban en MigrateAsync con InvalidOperationException de Npgsql.
Causa: el ConfigureAppConfiguration del test no llegaba a Program.cs a tiempo — la cadena de conexión se lee al registrar el DbContext, antes de que la config de test se aplicara.
Fix: sobrescribir el registro del DbContext en ConfigureTestServices (que sí corre después): RemoveAll + AddDbContext con la cadena del contenedor.

ConfigureTestServices no reconocido Build · CS1061

Síntoma: "IWebHostBuilder no contiene una definición para ConfigureTestServices".
Causa: el método es una extensión que vive en un namespace distinto al importado por defecto.
Fix: añadir using Microsoft.AspNetCore.TestHost;.

Warnings de nullable con el ctor de EF Build · CS8618

Síntoma: al añadir el constructor privado sin parámetros que necesita EF, las propiedades string no-nullable disparaban warnings.
Causa: el ctor vacío no inicializa esas propiedades; EF las rellena después por sus backing fields, pero el compilador no lo sabe.
Fix: patrón EF = null! en las propiedades string, declarando que EF garantiza el valor al rehidratar.

Puerto 5432 ya ocupado Infra · Docker

Síntoma: otro proyecto ya tenía un contenedor Postgres asociado al 5432.
Causa: colisión de puertos entre proyectos en la misma máquina.
Fix: mapear el host al 5433:5432 en docker-compose, aislando este proyecto.

API obsoleta de Testcontainers Test · warning

Síntoma: warning de deprecación del constructor PostgreSqlBuilder() sin parámetros.
Causa: la librería recomienda pasar la imagen al constructor para builds reproducibles.
Fix: new PostgreSqlBuilder("postgres:18-alpine") — build limpio sin warnings.

06 · Preparación para entrevista

Preguntas & respuestas modelo

¿No viola Clean Architecture que la Api referencie a Infrastructure?

No. El composition root (Program.cs) es la única excepción legítima: es donde se ensambla la inyección de dependencias. La regla de dependencia se cumple porque ningún controller ni entidad usa tipos concretos de Infrastructure — solo Program.cs los ve, y solo para registrarlos en el contenedor de DI.

¿Por qué el dominio no depende de nada?

Por la regla de dependencia: el dominio contiene las reglas de negocio, que son estables, y no debe conocer detalles volátiles como el ORM o la base de datos. Mantenerlo puro lo hace testeable en aislamiento (milisegundos, sin DB) y permite cambiar infraestructura sin tocar la lógica.

¿Anemic o Rich Domain Model?

Rich, cuando la entidad tiene invariantes que proteger. Meter las reglas en un service crea un modelo anémico: la entidad no garantiza su validez y cualquier código puede corromperla. Con constructores validadores y factory methods, los estados ilegales son irrepresentables — no dependes de que todos recuerden validar.

¿Cómo persistes un dominio rico con EF Core sin romper la encapsulación?

Con un constructor privado sin parámetros solo para EF (rehidrata sin ejecutar validación ni regenerar el Id) y propiedades de solo lectura que EF puebla por sus backing fields. Los factory methods siguen siendo el único camino público de creación.

¿Cómo guardas de forma segura un token de terceros?

Cifrado en reposo con una API que gestione las llaves (Data Protection), la columna fuera del modelo de dominio (shadow property), y verificado con un test que lee la columna cruda por SQL para confirmar que no está en texto plano.

¿Cómo evitas acoplar Infrastructure al framework web?

Con abstracciones. Un adapter que necesita el token del usuario no lee HttpContext directamente (eso lo ataría a ASP.NET); depende de IAccessTokenProvider, y la implementación que sí conoce HttpContext vive en la capa web. Así Infrastructure se testea sin un servidor HTTP.

¿Por qué el ownership check devuelve 404 y no 403?

Un 403 revela que el recurso existe pero no es tuyo. Devolver 404 para recursos ajenos no filtra su existencia — un usuario no puede deducir qué proyectos tienen otros. Es una decisión de seguridad, no de comodidad.

Dos records idénticos (AnalysisResult y ProjectGraph): ¿no viola DRY?

No. DRY es sobre no duplicar conocimiento o lógica, no sobre no repetir una forma. Son dos conceptos distintos (salida parcial de un analyzer vs grafo total persistido) que evolucionarán distinto; unificarlos por parecerse sería acoplamiento accidental.
