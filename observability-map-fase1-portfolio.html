// 01El problema

Para entender una app full-stack hay que revisar a mano el código, GitHub, la config, la base de datos… y armar el mapa mental uno mismo. No existe un lugar único que muestre cómo están conectadas las piezas.

La Fase 1 — Static Discovery resuelve la mitad de esa promesa: descubrir la arquitectura sin ejecutar el sistema, leyendo solo el código. El resultado es un grafo persistido, expuesto por una API segura, listo para dibujarse.

Entrada: un repo de GitHub conectado por OAuth Proceso: análisis multi-lenguaje (Roslyn + TS Compiler API) Salida: grafo Frontend→Backend→PostgreSQL con Source + Confidence

// 02Decisiones técnicas (el por qué)

T7 HttpClient tipado, no Octokit

El adapter de GitHub habla con la REST API a mano, con IHttpClientFactory.

¿Por qué? Cero dependencias nuevas, control total del logging del token, y dominio del protocolo (headers, paginación por Link). Octokit ocultaba justo lo que da valor de entrevista.

T8 Roslyn sintáctico, no semántico

El analyzer de C# razona sobre el árbol de sintaxis, sin type-checker.

¿Por qué? Leemos archivos sueltos de GitHub sin restaurar NuGet — la resolución semántica de tipos de framework no es viable. Es una inferencia honesta → por eso Confidence < 100.

T9 Subproceso Node por stdin

Un proceso Node con el TS Compiler API detecta React/TS; .NET le pasa los archivos por stdin (JSON) y recibe el resultado por stdout.

¿Por qué? No toca disco (nunca persistimos código ajeno), coherente con el modo sintáctico, y el seam hace testeable el mapeo sin Node instalado.

T10 Grafo grueso (nivel Application)

La detección fina (7+ clases/componentes) se agrega en 3 nodos: Frontend, Backend, PostgreSQL.

¿Por qué? El MVP muestra niveles System→Application, no Code. El detalle fino se conserva como evidencia (Source) de los edges gruesos, no como nodos.
Backend: ASP.NET Core · EF Core · PostgreSQL Análisis: Roslyn (C#) · TypeScript Compiler API (Node) Auth: GitHub OAuth · Data Protection Tests: xUnit · Testcontainers · node:test

// 04Qué hace, pieza por pieza

🔌 Conector de GitHub

Lista repos, lee el árbol de archivos y el contenido — con el token del usuario adjuntado por petición, nunca en logs. Paginación por header Link.

🧩 Analyzer C# (Roslyn)

Detecta Controllers, Services, Repositories y el DbContext por señales (atributo, herencia, sufijo) y sus dependencias por inyección de constructor — resolviendo interfaces a su implementación.

⚛️ Analyzer React/TS

Un subproceso Node clasifica componentes por carpeta y detecta llamadas fetch/axios con su URL — evidencia clave para conectar el frontend con el backend.

🕸️ Pipeline + agregación

Orquesta connector + analyzers y agrega la detección fina en el grafo de arquitectura, con Source y Confidence en cada relación.

🔐 Endpoint seguro

GET /projects/{id}/graph devuelve un DTO plano (nunca la entidad EF), con ownership check que responde 404 para proyectos ajenos.

✅ Probado de punta a punta

Desde el fixture de código hasta el grafo persistido: tests unitarios, de integración con Postgres real (Testcontainers) y del subproceso Node.

// 05Problemas técnicos y decisiones de robustez

Un bug real encontrado y resuelto, más las decisiones que previenen clases de bugs concretas (con su causa técnica y su fix).

🐞 Bug real · Build error NU1107

Conflicto de versiones de Roslyn

Síntoma: al añadir Microsoft.CodeAnalysis.CSharp 4.14.0, el restore falló con NU1107. Causa: EF Core Design ya arrastraba Roslyn 5.0.0 de forma transitiva; dos rutas pedían versiones incompatibles del mismo paquete (Microsoft.CodeAnalysis.Common).

Fix: referenciar explícitamente la versión que unifica el árbol (5.0.0), la misma que ya traía EF Core.
🛡️ Riesgo prevenido · Fuga de credenciales

El token de un usuario filtrándose a otro

Causa potencial: poner el Authorization en HttpClient.DefaultRequestHeaders — el handler se reutiliza (pool) entre peticiones y usuarios, así que el token de uno podría viajar en la petición de otro.

Fix: construir un HttpRequestMessage por llamada y adjuntar el token ahí. Vive solo el tiempo de esa petición.
🎯 Riesgo prevenido · Detección incompleta

Inyección por interfaz sin resolver

Causa: en Clean Architecture se inyectan interfaces (IProductService), pero el nodo detectado es la clase (ProductService). Un match ingenuo por nombre no conectaría el edge.

Fix: indexar cada nodo también por sus tipos base/interfaces, para que IProductService resuelva a ProductService.
🔒 Riesgo prevenido · Enumeración de recursos

403 filtrando la existencia de proyectos ajenos

Causa: responder 403 Forbidden a un proyecto de otro usuario le confirma al atacante que ese proyecto existe, permitiéndole enumerar IDs válidos.

Fix: responder 404 tanto si no existe como si no es tuyo → los dos casos son indistinguibles.
🧭 Riesgo prevenido · Relaciones inventadas

Dibujar un edge sin evidencia

Causa: asumir "hay frontend y hay backend, luego se conectan" crearía una relación sin origen — violando la regla de producto de no mostrar inferencias como hechos.

Fix: el edge Frontend→Backend solo se crea si hay al menos una apiCall detectada, y su Source es el archivo que la hace.
🔤 Riesgo prevenido · Contrato JSON roto

Desajuste de nombres entre .NET y Node

Causa: .NET serializa en PascalCase por defecto (Path/Content), pero el analyzer Node espera path/content; el contrato se rompería silenciosamente.

Fix: JsonSerializerOptions { PropertyNamingPolicy = CamelCase } en ambos sentidos (envío y deserialización).

// 06Preparación para entrevista

Preguntas reales sobre las decisiones de esta fase, con respuesta modelo.

¿Por qué IHttpClientFactory y no new HttpClient()?

Instanciar HttpClient a mano agota sockets (socket exhaustion): no libera las conexiones lo bastante rápido. IHttpClientFactory gestiona un pool de handlers reutilizables y renueva DNS. Se usa como typed client para inyectar el adapter ya configurado.

¿Cómo evitas filtrar el token de un usuario a otro?

No pongo el Authorization en los headers por defecto del HttpClient compartido, porque el handler se reutiliza entre peticiones. Construyo un HttpRequestMessage por llamada y adjunto el token ahí; así queda ligado solo a esa petición.

Análisis sintáctico vs semántico en Roslyn — ¿por qué elegiste sintáctico?

La resolución semántica necesita una Compilation con las DLLs referenciadas, y nosotros solo tenemos el texto de los archivos leídos de GitHub, sin restaurar NuGet. El sintáctico da casi todo el valor con una fracción de la complejidad. Como es una inferencia, no una verdad absoluta, todo edge sale con Confidence < 100.

¿Por qué el subproceso Node no construye los Node/Edge del dominio?

Porque son conceptos del dominio con invariantes (un edge estático no puede tener Confidence = 100). Si Node los construyera, esa regla de negocio viviría en JavaScript, fuera del dominio. Node detecta hechos; .NET los convierte al modelo común. Una sola fuente de verdad para las reglas.

Testeas algo que depende de que Node esté instalado. ¿Cómo?

Escondí la invocación del proceso detrás de una interfaz (INodeAnalyzerRunner). En los tests unitarios inyecto un runner falso que devuelve JSON fijo y pruebo el mapeo sin Node. La invocación real (Process.Start) se prueba en una suite de integración aparte. Es el mismo patrón que esconder HttpContext tras IAccessTokenProvider.

¿Por qué guardas las llamadas a API como metadata y no como un edge?

Porque todavía no sé qué nodo representa /api/products: crear un edge sería inventar una relación. Guardo la evidencia en el nodo que hace la llamada, y un paso posterior (el pipeline) la resuelve emparejándola con el backend. Nunca muestro una inferencia como un hecho.

¿Dónde va el ownership check y por qué?

En la capa Application (un use case), no en el controller. "Un usuario solo ve sus proyectos" es una regla de negocio, no un detalle de HTTP. El controller solo traduce la NotFoundException a un 404. Detecté que un endpoint viejo lo hacía inline en el controller y lo refactoricé para alinearlo.

404 vs 403 para un recurso ajeno — ¿cuál y por qué?

404. Un 403 confirma que el recurso existe, permitiendo enumerar IDs válidos. Con 404, "no existe" y "no es tuyo" son indistinguibles y no se filtra nada.
