STRATALENS · FULL-STACK ARCHITECTURE + OBSERVABILITY

Del repositorio a un mapa de arquitectura vivo, sin adivinar nada.

Stratalens conecta un repo de GitHub, lo analiza con compiladores reales (Roslyn, TS Compiler API) y dibuja cómo están conectadas sus piezas — Frontend, Backend, base de datos, seguridad, mensajería, workers, cloud — con trazabilidad y nivel de confianza en cada relación. Y cuando llega una request real, el mapa reacciona en vivo.

// 01El problema

Para entender cómo funciona de verdad una app full-stack, un dev tiene que revisar a mano el código, GitHub, la config, la infraestructura, los logs, las métricas… y armar el mapa mental él mismo. No existe un lugar único que muestre, de forma visual, cómo están conectadas las piezas — ni en diseño (qué existe) ni en tiempo real (qué está pasando ahora).

Stratalens resuelve las dos mitades: Static Discovery (lo que el código sugiere que existe) y Runtime Observability (lo que un trace real confirmó que ocurrió) — sin mezclarlas nunca sin etiquetar cuál es cuál.

Entrada: un repo de GitHub conectado por OAuth Proceso: análisis estático multi-stack + telemetría OpenTelemetry Salida: grafo interactivo con Source + Confidence, y modo LIVE

// 02El diferenciador: evidencia, no adivinanza

Existen herramientas que convierten una descripción en un diagrama pidiéndole a un LLM que "adivine" la arquitectura. Stratalens hace lo contrario: cada nodo y cada relación del mapa salen de evidencia real en el código — una clase parseada con Roslyn, una dependencia declarada en un package.json, un trace de OpenTelemetry observado.

🔒 Regla dura del dominio

Todo Edge lleva un Source (el archivo/config de donde se dedujo) y un Confidence. Es una invariante: es imposible construir una relación sin origen.

¿Por qué importa? El mapa nunca muestra una conexión que no pueda explicar de dónde salió. Ese es el valor: confianza en el dato.

🚫 Rechazar lo que se ve bien pero no es cierto

Durante el desarrollo se pidió una conexión Frontend→Security que quedaba estética. Se rechazó: no había evidencia de que el frontend hablara con la auth.

¿Por qué? Un diagrama honesto vale más que uno bonito pero inventado. Relajar la regla erosionaría la confianza en todo el mapa.

// 03Decisiones técnicas (el por qué)

Backend ASP.NET Core + Clean Architecture

4 proyectos: Domain · Application · Infrastructure · Api. Domain no referencia nada; Application define interfaces; Api nunca toca DbContext.

¿Por qué? Las reglas de negocio (qué es un nodo, cómo se calcula confidence) no dependen de PostgreSQL, GitHub ni Roslyn — se pueden testear y cambiar sin tocar infraestructura.

Analyzers Sistema de plugins (ILanguageAnalyzer)

El pipeline recibe los analyzers como IEnumerable<ILanguageAnalyzer> y corre los que apliquen. Añadir un stack = registrar una clase más.

¿Por qué? Cada categoría nueva (Security, Message Bus, Workers, Cloud) fue un analyzer independiente, sin tocar el pipeline ni romper nada. Abierto para extensión (O de SOLID).

C# Roslyn sintáctico, no semántico

El analyzer de C# razona sobre el árbol de sintaxis, sin restaurar NuGet ni type-checker.

¿Por qué? Leemos archivos sueltos de GitHub; la resolución semántica de tipos de framework no es viable. Es una inferencia honesta → por eso Confidence < 100.

React/TS Subproceso Node por stdin

Un proceso Node con el TS Compiler API detecta components/pages/services; .NET le pasa los archivos por stdin (JSON) y recibe el resultado por stdout, detrás de un seam.

¿Por qué? No toca disco (nunca persistimos código ajeno) y el seam hace testeable el mapeo sin Node instalado.

Runtime OpenTelemetry (OTLP protobuf real)

El demo exporta traces por OTLP/HTTP a un endpoint propio; se persisten como Trace/Span y promocionan edges a Confidence=100.

¿Por qué? Un edge confirmado por un trace real deja de ser inferencia. Es la materialización de "Static Discovery vs Runtime Observability".

LIVE SignalR con un Hub por proyecto

Al ingestar un trace, se emite un evento al grupo del proyecto; el frontend anima el recorrido en React Flow. Application no depende de SignalR (puerto ILiveTraceNotifier).

¿Por qué? El mapa reacciona en vivo sin acoplar la lógica de negocio a la tecnología de tiempo real.

// 06Funcionalidades

🔑 Login con GitHub OAuth

Autenticación + autorización para leer repos. El access_token se cifra en reposo con Data Protection API antes de persistirse; nunca aparece en logs ni respuestas.

📂 Conectar y analizar un repo

El usuario ve sus repos, elige uno, y el pipeline construye el grafo de forma síncrona. Re-análisis bajo demanda: reemplaza el grafo (idempotente).

🗺️ Grafo interactivo (React Flow)

Canvas con zoom/pan/selección, nodos custom estética "terminal", panel de detalle con la metadata y el Source de cada nodo.

🧩 Jerarquía expand/collapse

El Backend se expande en un contenedor con sus Controllers/Services dentro (contención real, no flechas). Layout size-aware para que nada se solape.

⚡ Modo LIVE

Una request real anima el recorrido Frontend→Backend→DB en el mapa, muestra la duración total, y distingue visualmente lo confirmado (runtime) de lo inferido (estático).

📊 Timeline de una request

Panel waterfall con los spans de un trace proporcionales a su duración — span raíz (backend) e hijo (query a la DB) con el total.

// 07Bugs reales (causa raíz + fix)

Los que más enseñaron. Todos diagnosticados a causa raíz, no parcheados en la superficie.

AUTH · seguridad

Endpoints protegidos daban 302 a GitHub en vez de 401

Causa: Program.cs tenía DefaultChallengeScheme = "GitHub", así que una request sin sesión redirigía al OAuth en vez de responder 401. Era invisible en los 114 tests porque la factory de test sustituía ese valor.

Fix: quitar el default explícito → cae al esquema Cookie, cuyo OnRedirectToLogin ya devolvía 401. El login real sigue pidiendo "GitHub" explícito. Verificado con curl real.
ANALYZERS · runtime

IOException: the pipe is being closed al analizar repos JSX reales

Causa: el runner del subproceso Node resolvía el script con un fallback (BaseDirectory/analyzers-node/…) que nunca existe en bin/. Node moría al instante y .NET reventaba escribiendo a un stdin ya cerrado — un error que no decía nada de la causa real.

Fix: portar a la DI el mismo algoritmo que ya usaban los tests (subir por el árbol buscando analyzers-node/src/analyze.mjs), con NODE_ANALYZER_SCRIPT como escape hatch para despliegues.
ANALYZERS · cobertura

El pipeline no detectaba nada en repos JSX puros ni backends Express

Causa: ReactTypeScriptAnalyzer exigía .ts/.tsx (el subproceso ya sabía parsear JSX, el bloqueo era el filtro .NET), y no existía ningún analyzer para Express.

Fix: ampliar el filtro a .js/.jsx y crear NodeExpressAnalyzer que confirma express/pg leyendo el package.json real (nunca infiere backend solo por convención de carpetas).
FRONTEND · layout

Al expandir el Backend, el contenedor chocaba con PostgreSQL/Docker

Causa: el contenedor expandido (~498px) es más ancho que el LAYER_WIDTH fijo (400px), así que se metía en la columna de la capa siguiente.

Fix: layout size-aware — la X de cada capa parte del ancho REAL de la anterior, y dentro de una capa los nodos se apilan por su alto real. Un contenedor ancho ahora empuja lo siguiente a la derecha sin solaparse.
FRONTEND · legibilidad

Las etiquetas de los edges eran ilegibles sobre el canvas oscuro

Causa: React Flow pinta el fondo de la etiqueta al 75% de opacidad por defecto (su CSS base), así que sobre el fondo oscuro con glow el texto se mezclaba.

Fix: forzar fillOpacity:1 + padding + radio → una píldora opaca y legible de verdad.
RUNTIME · invariante de dominio

El primer trace en frío rompía la invariante "un solo span raíz"

Causa: con el demo frío, la primera request parte los spans en 2 batches OTLP; el batch del span hijo llega sin su raíz, violando la asunción del MVP (un trace = un span raíz).

Fix: documentado como límite conocido del MVP; con el demo caliente los spans van juntos y el trace promueve el edge a runtime correctamente. Diagnóstico honesto > parche que oculte la asunción.

// 08Preparación para entrevista

¿Por qué separar Static Discovery de Runtime Observability?
Porque responden preguntas distintas: lo estático dice "qué existe según el código" (una inferencia), lo runtime dice "qué ocurrió de verdad" (un hecho observado). Mezclarlas sin etiquetar engañaría al usuario. Lo materialicé como una invariante: un edge estático tiene Confidence < 100; solo un trace real produce Confidence = 100.
¿Por qué usar Roslyn / TS Compiler y no pedirle a un LLM que arme el diagrama?
Porque el valor del producto es la confianza en el dato. Un LLM adivina; un compilador parsea el AST real. Mi analyzer extrae Controllers/Services del árbol de sintaxis de C# y detecta dependencias del package.json real — cada relación es verificable contra un archivo concreto. Es determinista, testeable y honesto.
¿Por qué Confidence < 100 es una invariante de dominio y no una convención?
Porque una convención se puede violar sin querer; una invariante no. La entidad Edge tiene constructor privado + factory methods: FromStaticAnalysis valida 0..99, y FromRuntimeTrace es el ÚNICO camino que produce 100. Así "confidence 100 solo viene de runtime" se cumple por construcción, no por disciplina.
¿Cómo modelaste la jerarquía de nodos en una base relacional?
Con el patrón Adjacency List: un campo ParentNodeId nullable (null = raíz). Para un árbol poco profundo es la elección correcta — nested sets o closure table resuelven problemas que no tengo. "Máximo un padre" queda garantizado por construcción (un solo campo), y la auto-referencia es imposible porque el Id se genera dentro del constructor: validarla sería código muerto.
¿Cómo evitás que el mapa invente relaciones?
Cada Edge exige un Source no vacío como invariante de dominio, y cada analyzer confirma con evidencia real (una dependencia declarada, no una carpeta con cierto nombre). Incluso rechacé una conexión que un usuario me pidió porque no tenía respaldo en el código — preferí el diagrama honesto.
¿Cómo evitás que las capas de Clean Architecture se filtren?
Por las referencias de proyecto: Domain no referencia nada, Application solo define interfaces (IGraphRepository, ILanguageAnalyzer…), y Api nunca inyecta DbContext directo. El caso de uso no sabe que detrás hay PostgreSQL, GitHub ni Roslyn — solo depende de abstracciones (D de SOLID).
¿Cómo autenticás el endpoint de telemetría, que lo llama una máquina y no un usuario?
Con una clave de ingesta por proyecto (auth máquina-a-máquina), hasheada con SHA-256 en la base — el endpoint OTLP no depende de una cookie de sesión. Todo el resto de la API sí exige auth de usuario; login/callback de OAuth son la única excepción.
¿Por qué un sistema de plugins para los analyzers?
Porque el catálogo de stacks crece. El pipeline recibe IEnumerable<ILanguageAnalyzer> y corre los que apliquen; añadir Security, Message Bus, Workers o Cloud fue registrar una clase más, sin tocar el orquestador. Un test de integración me recordó que eso también aplica a los tests: solo ejercitan lo que conectás en su setup.
